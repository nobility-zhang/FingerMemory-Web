## 每个切片的提交纪律

用户已明确要求“每实现一部分就提交一部分”，后续执行者可以并且应当自行创建本地 Git commit，不要再因之前提示里的“未授权不提交”而停在未提交状态。推送、发布、真实部署仍需单独指令。

每个小任务顺序固定为：检查工作区归属 → 实现 → 针对性验证 → 读 diff → 更新任务状态/验证说明 → 只暂存本任务及必要依赖 → 检查 staged diff → commit → 读取提交与剩余状态。提交完成后才能将任务标为“已完成并提交”，并在下一次记录写入实际短 SHA。提交自身文档可以写任务 ID，SHA 在后续更新或交付中补充，不尝试把自身 SHA 写进自身提交。

- 不能用“计划提交”“文件已写”“测试通过”替代真实提交结果；没有 commit SHA 的任务保持“未提交”。
- 每个切片须有用户可观察行为或清晰的基础能力，不按文件数量凑提交，也不等全部 G 阶段做完才一起提交。
- 如果部分暂存，工作区测试通过不代表暂存快照可构建；在隔离副本/临时索引或等价环境验证提交候选及依赖。不通过删测试、重置工作区或覆盖文件来切分历史。
- 不使用 blanket `git add .` 吞入未知文件、数据库、秘密、日志或临时素材；确认应提交的成品资产、来源清单和必要 fixture。
- 不改写旧提交时间、作者或宣称补交等于当时已提交；不强推、不 stash/drop 用户工作、不 `reset --hard`。
- 执行失败时保留改动和真实原因。可读/测试/普通提交在已授权范围内自主处理；需要宿主写权限时按工具授权处理，不能伪称 Git 成功。

### 已核实的问题

- 密码直接存储和比较明文；仓库 SQL 还包含演示明文密码。新版本地应用不迁移账号体系。
- 单词更新和删除只检查登录，不检查内容归属；Koa 内容写入也只检查会话存在，没有资源所有者模型。
- 笔记弹窗切换编辑状态时只修改组件局部 `text`，没有保存 API；Java 侧笔记只有 Mapper，没有完整写入接口。笔记展示随机取某位用户的笔记，而不是当前用户笔记。
- `NoteMapper` 的“按词和作者查询”参数标注把两个参数都命名为 `wordId`，当前没有调用方，但该查询不可按现有签名正确使用。
- Koa Redis session 工具的 `setAttribute` 调用了不存在的 `promiseHSet`，与 Java 共用会话的写入路径不可靠。
- 旧前端单元测试只有初始化示例；Java Mapper 测试依赖本机 MySQL 且共享固定账号/分类名，不能证明隔离运行；Koa 没有测试脚本。
- npm 锁文件来自 2021 年的淘宝镜像，Vue/Webpack 工具链是旧主版本，不应在 Node 24 上直接继续作为新版基线。

### 实际数据情况

- 两个仓库的 Git 历史中都没有真实词表、缓存、`history.log`、数据库转储或备份文件。
- `fm.sql` 是可重建的演示数据，不是运行时数据库；包含 21 个用户、21 本图书、23 个单词、21 个词库、21 条笔记、46 条词库单词关系以及收藏关系。
- `public/*.json5` 是 MockJS 假数据模板，不是个人词库。
- 因此当前没有可执行的个人数据迁移，也没有迁移完成声明。迁移边界和未来适配器已写入架构文档。
